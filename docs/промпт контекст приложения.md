# 1. О проекте

**Arterio** — приложение для самопознания, самоанализа и личного развития.

Основная идея — создать личное цифровое пространство, в котором пользователь может фиксировать свои мысли, отслеживать эмоциональное состояние и возвращаться к важным событиям своей жизни.

Мы разрабатываем первую упрощённую версию продукта — **Arterio Mini**.

Главный принцип продукта:

> A personal space for thoughts, emotions and self-reflection.

Интерфейс должен восприниматься как личное пространство пользователя, а не как корпоративная панель управления или приложение для повышения продуктивности.

## Основные модули Arterio Mini

В первой версии предусмотрено только три основных функциональных направления.

### 1. Insights

Пространство для фиксации мыслей, идей, наблюдений и личных открытий.

Пользователь может:

- Создавать записи.
- Просматривать список записей.
- Открывать отдельную запись.
- Редактировать записи.
- Удалять записи.

### 2. Mood

Пространство для фиксации эмоционального состояния.

Пользователь может:

- Выбирать настроение.
- Описывать свой день.
- Создавать записи о своём эмоциональном состоянии.
- Просматривать историю записей.
- Редактировать и удалять записи.

### 3. Activity

Общая хронологическая лента активности пользователя.

Она объединяет события из Insights и Mood и отображает их в хронологическом порядке с группировкой по датам.

Activity не является отдельной системой создания записей. Это единое представление уже существующих данных.

# 2. Структура приложения

Основные страницы:

- **Overview** — главная страница, личное пространство пользователя.
- **Insights** — работа с мыслями и идеями.
- **Mood** — работа с эмоциональным состоянием.
- **Activity** — общая история активности.

## Концепция Overview

Главная страница должна быть оформлена как Personal Space.

Предполагаемые блоки:

1. Welcome Section — приветствие и текущая дата.
2. Daily Check-in — карточка для фиксации настроения за день.
3. Quick Actions — быстрые действия New Insight и New Mood.
4. Recent Activity — последние записи пользователя.
5. Inspiration — небольшая вдохновляющая цитата или напоминание.

Overview не должна превращаться в перегруженный Dashboard.

Не добавляй графики, сложную статистику, систему достижений и дополнительные модули без отдельного запроса.

# 4. Архитектура проекта

В проекте используется **Feature-Sliced Design (FSD)**.

Основные слои:

- `app` — инициализация приложения, провайдеры, роутер, глобальные стили.
- `pages` — страницы приложения.
- `widgets` — крупные композиционные блоки интерфейса.
- `features` — пользовательские сценарии и действия.
- `entities` — бизнес-сущности и связанная с ними логика.
- `shared` — переиспользуемые компоненты, утилиты, конфигурации и ресурсы.

## Пример предполагаемой структуры

```text
src/
├── app/
│   ├── App.tsx
│   ├── main.tsx
│   ├── providers/
│   ├── styles/
│   │   ├── index.scss
│   │   └── variables.scss
│   └── ...
│
├── pages/
│   ├── overview-page/
│   ├── insights-page/
│   ├── mood-page/
│   └── activity-page/
│
├── widgets/
│   ├── sidebar/
│   ├── daily-check-in/
│   ├── recent-activity/
│   ├── insights-list/
│   ├── mood-history/
│   └── activity-timeline/
│
├── features/
│   ├── create-insight/
│   ├── edit-insight/
│   ├── delete-insight/
│   ├── create-mood/
│   ├── edit-mood/
│   └── delete-mood/
│
├── entities/
│   ├── insight/
│   └── mood-entry/
│
└── shared/
    ├── ui/
    ├── lib/
    ├── config/
    └── assets/
```

Это ориентир, а не требование создавать все директории заранее.

Создавай структуру по мере появления реальной необходимости.

## Правила FSD

- Соблюдай направление зависимостей между слоями.
- Не допускай импортов из вышестоящих слоёв в нижестоящие.
- Не размещай бизнес-логику в `shared`.
- Не смешивай пользовательские сценарии, сущности и UI-композиции.
- Не создавай отдельную директорию для каждой мелочи.
- Избегай чрезмерной декомпозиции.

Архитектура должна оставаться понятной и оправданной масштабом приложения.

# 5. Управление состоянием и хранение данных

На текущем этапе приложение работает без backend.

Используем:

- Redux Toolkit для глобального состояния.
- Redux Persist для сохранения необходимых данных.
- localStorage как первоначальное хранилище.

Пользовательские данные должны сохраняться между перезагрузками страницы.

При этом:

- Не обращайся к localStorage непосредственно из React-компонентов.
- Не храни в Redux временное состояние интерфейса без необходимости.
- Не сохраняй в Redux Persist лишние данные.
- Отделяй работу с данными от UI.
- Используй TypeScript-типы для сущностей и состояния.

В будущем возможно подключение Supabase или другого backend.

Поэтому архитектура не должна создавать сильную зависимость UI от конкретного способа хранения данных.

Не добавляй backend, авторизацию, базу данных, IndexedDB и сложную инфраструктуру без отдельного запроса.

# 6. Дизайн и визуальная концепция

Основное направление дизайна:

**Soft & Friendly / Soft Modern Wellness**

Интерфейс должен быть:

- Современным.
- Минималистичным.
- Светлым.
- Дружелюбным.
- Визуально лёгким.
- Эстетичным, но не детским.
- Удобным для ежедневного использования.

В качестве визуального ориентира используется мягкий современный wellness-дизайн с бирюзовым акцентом, светлым фоном и белыми карточками.

## Цветовая палитра

Используй следующие значения как основу дизайн-системы:

| Назначение     | Цвет      |
| -------------- | --------- |
| Primary        | `#59D5D5` |
| Background     | `#F4F6F7` |
| Surface        | `#FFFFFF` |
| Text Primary   | `#20242B` |
| Text Secondary | `#929BA4` |
| Accent Soft    | `#DDF5F3` |
| Mood Accent    | `#F7E8E9` |
| Inspiration    | `#E8E5F2` |

Бирюзовый Primary должен оставаться свежим и заметным, как в исходном дизайн-референсе.

Не заменяй его на тёмный, серый или чрезмерно приглушённый оттенок.

## Типографика

- Заголовки: Manrope.
- Основной текст: Inter.

Используй понятную иерархию размеров, весов и межстрочных интервалов.

## Скругления

```scss
$radius-sm: 8px;
$radius-md: 12px;
$radius-lg: 16px;
$radius-xl: 20px;
$radius-full: 9999px;
```

## Визуальные принципы

- Много свободного пространства.
- Белые карточки на светлом фоне.
- Мягкие скругления.
- Лёгкие тени.
- Деликатные границы.
- Единообразные иконки.
- Аккуратные hover- и focus-состояния.
- Понятная визуальная иерархия.
- Адаптивность.

Не используй:

- Кислотные цвета.
- Чрезмерно яркие градиенты.
- Мультяшный стиль.
- Избыточное количество эмодзи.
- Игровые награды и достижения.
- Слишком много декоративных элементов.
- Сложные анимации без необходимости.

# 7. Правила разработки компонентов

При написании кода придерживайся следующих принципов:

1. Используй функциональные React-компоненты.
2. Используй TypeScript и явно описывай типы там, где это повышает понятность.
3. Избегай `any`, если есть возможность определить корректный тип.
4. Разделяй UI и бизнес-логику.
5. Не создавай огромные компоненты, отвечающие за всё сразу.
6. Используй SCSS Modules для локальных стилей.
7. Глобальные стили и переменные размещай в `app/styles`.
8. Переиспользуй общие UI-компоненты, когда это действительно оправдано.
9. Используй Ant Design там, где он подходит, но не пытайся построить на нём абсолютно весь интерфейс.
10. Следи за семантикой HTML и доступностью.
11. Учитывай адаптивность интерфейса.
12. Не усложняй решения ради абстрактной универсальности.

# 10. Главный принцип проекта

Arterio должен развиваться как качественный, аккуратный и продуманный frontend-проект, а не как набор случайно добавленных функций.

Принимай решения с учётом трёх приоритетов:

1. **Maintainability** — код должен быть понятным и поддерживаемым.
2. **User Experience** — интерфейс должен быть приятным и удобным.
3. **Simplicity** — не усложняй приложение раньше времени.

Всегда учитывай существующий контекст проекта и продолжай развитие Arterio с того места, на котором мы остановились.

Если для конкретной задачи не хватает информации о текущем коде, сначала попроси показать соответствующий файл или структуру. Не выдумывай существующие реализации и не делай вид, что знаешь содержимое файлов.
